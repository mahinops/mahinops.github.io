Arrays vs Slices

A slice is a tiny window (pointer, length, capacity) looking at an array that lives elsewhere.

The idea

An array is a fixed row of lockers: [3]int is exactly 3 lockers, forever, and copying it copies all the contents.

A slice is a see-through frame laid over a row of lockers. The frame stores three things: where it starts (ptr), how many lockers you can see (len) and how many lockers there are from the start to the end of the row (cap). Two frames can sit over the same row, so editing through one is visible through the other. When append runs out of room, Go builds a bigger row, copies everything over and moves the frame to it.

Try it

  • In “append and growth” start with cap = len and append once: watch the new array appear.
  • In “Aliasing” change nothing, step through, and find the exact step where a changes although we only touched b.
  • In “Full slice expression” compare with the aliasing example: why does a NOT change this time?
  • Increase the number of appends to 9 and read the capacities. Do they grow every time?

Common mistakes

  • Assuming b := a[1:3] copies the data. It does not; it shares the same array.
  • Appending to a sub-slice can silently overwrite the original’s later elements (see Aliasing).
  • Forgetting s = append(s, x): append returns the new slice; ignoring it loses the result.
  • Relying on exact capacities. Doubling is what you will see for small slices today, but it is a runtime detail that can change between Go versions.
