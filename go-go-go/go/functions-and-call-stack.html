Functions and the Call Stack

Every function call gets its own frame: a private scratch-pad, stacked on top of the caller’s.

The idea

Picture a stack of sticky notes on your desk. You are working on a task (main). You need a sub-task done, so you put a fresh note on top with the inputs written on it and work only on that note. When it is finished you read off the answer, throw the note away, and carry on with the one underneath.

Arguments are copied onto the new note, so the callee can scribble on its notes without touching yours. A function that calls itself (recursion) just keeps adding notes until it reaches a case it can answer immediately, then the answers flow back down the stack.

Watch it work

Try it

  • In “Recursion” set n to 1, then 4, then 8. How many frames exist at the deepest point?
  • In “Multiple return values” set b to 1 and then 7. Watch q and r.
  • Notice the callee never changes the caller’s variables. Its inputs were copies.

Common mistakes

  • Forgetting the base case in recursion. The stack grows until Go reports a stack overflow: fatal error: stack overflow.
  • Expecting a function to modify your variable when you passed a copy. Pass a pointer if it must.
  • Ignoring an error result: v, _ := f() throws away the information that tells you it failed.
  • Unused function parameters are fine, but unused local variables are a compile error.
